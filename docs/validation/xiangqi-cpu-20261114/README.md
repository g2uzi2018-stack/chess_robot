# 中国象棋识别 CPU 与内存优化 · 2026-11-14

已部署至 Jetson 的独立冻结目录。保持 1280×720、30 Hz、曝光 25000 μs / gain16、原模型与类别/几何判定规则。此次没有机械臂使能、运动或参考恢复。

## 结果

下表为同一现场 32 子、同一固定时钟配置的三个 60 秒窗口。网页流处于空闲状态；CPU 来自 /proc 累计时间，12 核全部满载记为整机 100%，一个满核记为进程 1.0 核。观察程序额外占约 0.21 核，三个窗口均计入整机值。延迟从相机节点收到帧的时间戳算到观察程序收到结果，不包含曝光之前或浏览器显示时间。

| 指标 | 优化前 | 上线后首轮 | 上线后复测 |
|---|---:|---:|---:|
| 整机 CPU | 55.41% | 55.76% | 54.16% |
| 视觉进程合计 / 核 | 5.864 | 5.919 | 5.669 |
| 相机进程 / 核 | 1.808 | 1.752 | 1.752 |
| scene 进程 / 核 | 1.004 | 0.894 | 0.881 |
| 两个推理宿主进程 / 核 | 1.067 | 1.278 | 1.049 |
| 识别 / Hz | 29.885 | 29.973 | 29.916 |
| scene / Hz | 29.682 | 29.952 | 29.922 |
| 相机 / Hz | 30.023 | 30.017 | 30.016 |
| scene 延迟中位 / ms | 242.87 | 168.63 | 154.58 |
| scene 延迟 95 分位 / ms | 286.90 | 209.75 | 203.77 |
| 跟踪阶段中位 / ms | 7.69 | 4.28 | 4.29 |

相机与 scene 的 CPU 降幅分别约 3.1%、11.0%–12.3%。整机收益较小，推理宿主进程占用存在明显跨窗口波动；首轮整机 CPU 没有降低，不能只用最后一个窗口宣称稳定的大幅节省。当前证据不支持直接增加一倍摄像头数量。

较明确的收益是结果送达延迟下降：scene 排队时间中位从约 95 ms 降至首轮约 11 ms，避免处理积压。识别仍接近 30 Hz。各窗口全部结果均保留 32 个检测，相机硬件帧号观测缺口为 0；这不等于每枚棋子的类别和几何每帧都合格，更不等于人工真值准确率。

最终检查：三个视觉服务 active/running，两个 IP 网页返回 200，基座变换有效、32 个检测。scene 生命周期内 4 次过期拒绝均发生在启动期，此后未新增。部分帧仍因类别或几何不完整而不能形成整盘抓取快照，未通过放宽门限隐藏此情况。

## 改动

- 相机复用约 6.15 MiB 的彩色/浮点深度发布缓冲，将处理结果直接写入缓冲，省去每帧重新分配和写入 ROS Image 前的额外整图复制。ROS 传输自身仍有复制，不宣称端到端零拷贝。
- 用 256 KiB 的深度查表合并最近邻重映射、单位换算和缺失深度 NaN 填充。保持 SDK RGB-D 对齐、彩色线性插值、深度最近邻、边界及零深度语义。
- 固定 URDF 拓扑与变换矩阵初始化时缓存，每帧仍使用当前关节值计算，未缓存过期位姿。
- scene 消费消息只进行一次完整校验，保留字段、数值、大小、时间戳和序号资格检查。通用 JSON 解码入口仍拒绝 NaN/Infinity。
- 跟踪状态继续每帧更新、发布，磁盘检查点改为首次、每秒及正常退出写入。意外断电最多损失约一秒的磁盘检查点；每次 scene 使用独立会话文件，不据此恢复机械臂参考。

- 250 个关节姿态、20 个链路的 FK 对照最大绝对误差 4.44e-16。FK 耗时 1.882→0.208 ms。
- 14 类正常/异常 JSON 输入的接受或拒绝结果一致。解码加校验耗时 8.340→5.356 ms。
- 160 帧跟踪逐帧输出一致；检查点写入 160→6 次，首次/间隔/退出最终状态均核对。
- 线程数 4→2 的 CPU 时间没有收益，4→1 的处理墙钟超过单帧 33.3 ms 预算，保留 4 线程。
- 离线 CUDA 阻塞等待实验输出签名一致，但 CPU 时间 54.48→54.53 ms，未采用。官方语义参考 [NVIDIA CUDA 12.6.3 Primary Context 文档](https://docs.nvidia.com/cuda/archive/12.6.3/cuda-driver-api/group__CUDA__PRIMARY__CTX.html)。
