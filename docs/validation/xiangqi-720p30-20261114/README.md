# 固定 1280×720 / 30 Hz 的识别帧率恢复 · 2026-11-14

用户明确选择保持 1280×720、30 Hz，相机配置未降低分辨率、未提升采集帧率、曝光仍为 25000 μs / gain16。没有机器人运动或夹爪命令。

## 原因与证据

相机硬件没有降速。初始 40 秒只读观测收到 1,200 个 FrameInfo，30.0026 fps，硬件帧号无缺口；识别 881 帧，22.0769 fps，结果序号无缺口。识别进程内部计数进一步表明：信息小消息约 30.02 Hz，彩色图 25.98 Hz、深度图 26.31 Hz、配齐并选择的 RGB-D 约 23.01 Hz。该窗口没有主动跳过积压的完整输入。大图缺失发生在同帧配对之前，不是几何或类别阈值过滤了最终结果。

发现相机与渲染器的 DDS GUID 首四字节是 `010f6710`，新识别进程是 `010febdb`。昨天 Wi-Fi 地址由 192.168.20.75 变化为 192.168.20.240，而相机/渲染器进程保持运行；新启动的识别进程获得了不同主机标识。Fast DDS 使用 GUID 前四字节识别同机参与者，旧版本 SHM locator 也使用基于 IP 的主机 ID。结果同机的大图流走 UDP，8 秒观察到 UDP RcvbufErrors 增加 414。

这与 [Fast DDS 官方 SHM 说明](https://fast-dds.docs.eprosima.com/en/stable/fastdds/transport/shared_memory/shared_memory.html) 和 [网络变化导致主机识别不一致的上游问题](https://github.com/eProsima/Fast-DDS/issues/865) 相符。现场 GUID、丢包与重连前后的数据共同支持此诊断，不仅依据上游文档推断。

同时，旧识别启动脚本未加载相机已有的大图传输配置。单独补上该配置并未完全解决问题（约 24.8 fps），不能把它当作唯一修复。随后只重连相机/预览服务和渲染服务，使它们与识别进程使用当前网络下的一致主机标识：四路输入和选中输入均恢复到 29.997 Hz，识别发布约 29.89 fps。

第二个瓶颈是同帧 ROI 补查。初始 881 帧中 499 帧需补查；无补查、1 处、2 处补查的 GPU worker 耗时中位数分别约 28.4 / 43.5 / 51.4 ms。worker 含预后处理，不能把它当成纯 GPU kernel 时间。整体 GPU 利用率采样仅 13–55%，CPU/GPU 频率约 2.2016/1.3005 GHz。因此保留补查，用两个独立推理进程重叠运行；这本身先把约 22 fps 提至约 24 fps，传输重连后才达到约 30 fps。

## 交付改动

- 快速识别路径使用两个 GPU worker、两个几何 worker、四个有所有权的 RGB-D 槽；最多三个 GPU 在途/排队任务。旧无分类器路径仍为一个 GPU worker、三个槽。
- 保留原任务号/时间戳配对、槽锁和按输入顺序交付；没有复用旧图像或把预测重复计为新帧。
- 清理监督器兼容三槽和四槽，并继续要求 token、owner PID 与命名规则一致。
- 两个标准启动入口加载既有大图 Fast DDS 配置；现场冻结启动脚本显式使用安装版本的同一配置。
- 每三秒状态文件增加各输入接收计数与配对选择计数，方便定位输入损失。`submitted_rgbd` 在选择完整四元组时计数，位于图像资格检查之前；测量窗口无输入资格拒绝时才等同于提交数。

模型、类别置信度阈值、同帧补查、上一轮位置恢复估计器均未修改。修复关注吞吐，不能把类别齐全率当作人工真值准确率。

## 验收

最终连续观测见 `final-live-summary.json`；原始逐帧数据在远端审计目录。观测同时打开远端 IP 网页请求新图像，识别、scene 与相机分别统计；使用源帧时间戳和结果序号排除重复帧，另核对生产进程自身发布计数。

三槽/四槽资源清理的临时内存核验均通过：错误 token 被拒绝、正确 owner 的所有块被删除；临时文件随 TemporaryDirectory 删除。未运行冒烟测试，没有持久化测试源码。
